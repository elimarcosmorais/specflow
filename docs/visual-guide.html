Guia visual do framework agent-spec

Como usar as skills, os agents, as rules e os utilitários do fluxo SDD. Clique em qualquer caixa de um diagrama para ver os detalhes.

Por onde começar

O framework tem duas portas de entrada: preparar o projeto (uma vez só) e começar uma mudança (toda vez que surge uma ideia). Os dois diagramas abaixo mostram cada uma.

Regra de ouro: aprovação entre fases. Cada documento nasce rascunho. A próxima fase só começa depois que você revisa e aprova o documento anterior (muda para aprovado). É isso que impede a IA de construir em cima de um entendimento errado.

Primeiro uso, em 4 passos

  1. Copie a pasta .claude/ para o projeto. Ela leva as skills, os agents e o rules/behavior.md.
  2. Escreva o pedido em docs/references/prompts/AAAA-MM-DD-assunto.md, ou use texto livre.
  3. Rode /agent-spec-pre-refinement com o pedido. O documento gerado termina com a seção Próximo passo, com o comando pronto para copiar.
  4. A cada fase: leia, ajuste, aprove e rode o comando do Próximo passo.

Perdeu o fio?

O /agent-spec-guide lê o estado da feature (versão, documentos, status) e diz qual é o próximo passo:

/agent-spec-guide "qual o próximo passo da 001?"

O guia só consulta: ele nunca cria arquivos nem roda a skill que recomenda.

Fluxo completo de uma feature

A espinha do framework é uma sequência: cada fase usa como entrada o documento aprovado da fase anterior. Em volta dela ficam as transversais (ADR, Debt), que entram quando aparece uma decisão de arquitetura ou quando se decide pagar débitos. O design system entra uma vez, antes do Design da primeira feature com telas, e depois só é atualizado quando fica defasado.

A pergunta que cada fase responde

FasePerguntaGera

Quando registrar uma ADR

A ADR não tem lugar fixo na fila: ela é registrada quando a decisão aparece e precisa existir antes da fase que depende dela.

  • Recomendada pelo Pre-Refinement (fundação: stack, arquitetura) → registre antes do PRD. Prazo limite: antes do Tech Alignment, que trata as ADRs aceito como restrições.
  • Candidata do Tech Alignment (uma D-NN que vale para o projeto todo) → registre antes da Spec.
  • Decisão nova que contradiz uma ADR aceita não edita a antiga: cria outra, e a antiga vira substituído.

Execução por dentro

A skill agent-spec-run-tasks não escreve código: ela coordena três agents, uma task de cada vez, na ordem das dependências. As caixas verdes são os agents.

Gravidade dos problemas

GravidadeO que acontece
crítica / altaBloqueia. A task volta para o executor corrigir (até 2 correções).
média / baixaNão bloqueia. Vira débito no debts.md da versão e a task é concluída.

Por que fica em stage e não é commitado

A task aprovada recebe git add, mas não é commitada. Como o trabalho das tasks anteriores já está em stage, git diff mostra só o que a task da vez mudou. É assim que a revisão isola cada task. No fim, o commit é seu: /agent-spec-semantic-commit.

Versões e tamanho da mudança

Uma versão já implementada nunca é editada: uma mudança posterior abre v2, v3… O tamanho da mudança define em que fase ela entra e quais documentos a nova versão tem.

Exemplo: qual documento vale agora?

Uma feature com 3 versões: v1 (entrega), v2 (mudança pequena) e v3 (débitos). O estado atual de cada documento é o da versão mais recente em que ele aparece (em verde). Cada documento presente é completo, não um diff.

Documentov1 · grandev2 · pequenav3 · débitos
pre-refinement.mdv1v2 ✔—
prd.mdv1 ✔——
tech-alignment.mdv1 ✔——
spec.mdv1v2 ✔—
tasks.md + tasks/v1v2v3 ✔
debts.mdv1v2—

O debts.md não tem uma versão vigente: cada versão tem o seu, e a fase Debt lê os débitos aberto de todos eles.

Débito × mudança pequena: pagar débito não muda comportamento, por isso a versão de débitos não tem spec.md. Se a correção mudaria API, erros, dados ou regras, não é débito: é mudança, e segue o fluxo normal.

Rules e contexto: o que o agente sabe sobre o projeto

Nem tudo entra no contexto do agente ao mesmo tempo. O CLAUDE.md e o behavior.md carregam sempre; as rules por área só carregam quando o agente toca os arquivos delas; ADRs e design system são lidos quando um documento os cita.

Anatomia de uma rule por área

# .claude/rules/database-access.md
---
paths:
  - src/db/**
  - docs/specs/**   # carrega também na spec e nas tasks
---
# Acesso a banco
provisória   # → estável quando o tema ganha código

- Repositório recebe a conexão por parâmetro.
  Porquê: facilita o teste com banco em memória.
  ✅ new UserRepo(db)   ❌ import { db } dentro do repo

Rule × ADR × CLAUDE.md

  • ADR registra a decisão, as alternativas e o porquê. Não carrega no contexto.
  • Rule diz ao agente como aplicar a decisão (uma linha + exemplo). Carrega ao tocar os paths.
  • CLAUDE.md traz o transversal (stack, comandos, convenções globais). Carrega sempre.
  • behavior.md é do framework, não do projeto: as 4 regras de comportamento. Carrega sempre.
  • README é para pessoas, não para o agente.

Mapa de tudo

Todas as peças do framework, por tipo. Fases geram um documento do fluxo; agents são chamados pela Execução; utilitários ajudam em qualquer momento, sem gerar documento de fase; rules são o contexto que carrega sozinho.

Documentos, IDs e status

Os documentos de uma feature ficam juntos, por versão. Os IDs numerados criam uma trilha do pedido até o commit: dá para saber de qual critério de aceite veio cada teste e de qual teste veio cada task.

Ciclo de status

Documentos de fase e design-system.mdrascunho→aprovado
ADRproposto→aceito→substituído
Task (T*.md)pendente→em andamento→concluída
Débito (no debts.md)aberto→pago
Rule por áreaprovisória→estável

Convenções

  • Nomes em kebab-case, sem acento: 001-login-com-google.
  • Numeração de 3 dígitos por pasta (features/, adr/); número nunca é reaproveitado.
  • Tasks recomeçam em T1 a cada versão.
  • Todo documento de fase termina com Próximo passo e o comando pronto para copiar.
  • Pastas só são criadas quando usadas.
