## 1. Objetivo

O CRUD de Projetos funciona de ponta a ponta no motor: o repositório SQLite implementa
`Repository`, e o handler expõe as 4 rotas `/api/projects`. A integração prova tudo com banco
real, API real, token, banco indisponível e cópia da instalação para outra pasta.

## 2. O que fazer

- `sqlite_repository.go`, `NewSQLiteRepository(db *sql.DB)` implementando `Repository` (T7):
  - SQL sempre com parâmetros (`?`).
  - Datas em texto RFC 3339, UTC.
  - Violação do `UNIQUE` de `name_key` → `project.name_taken`; de `path_key` →
    `project.path_taken` (RN-13, RN-14, corrida).
  - `sql.ErrNoRows`, ou nenhuma linha afetada em `Update`/`Delete` → `project.not_found`.
  - `DB` nulo ou qualquer outro erro do SQLite → `apperr.ErrDatabaseUnavailable` com a causa
    (D-06).
- `handler.go`, `Routes(s)`:
  - As 4 rotas, todas protegidas:
    - `GET /api/projects` → `200 {items: Project[]}`;
    - `POST /api/projects` → `201 Project`;
    - `PUT /api/projects/{id}` → `200 Project`;
    - `DELETE /api/projects/{id}` → `204`.
  - DTO de saída `Project` exatamente como em §3.1: `id`, `name`, `path` absoluto, `type`,
    `folderExists`, `createdAt` e `updatedAt` em RFC 3339 UTC.
  - DTO de entrada `{name, path, type}` lido com `DecodeJSON`: campo desconhecido → `400`;
    campo ausente → string vazia.
  - `{id}` que não é inteiro positivo → `404 project.not_found`.
  - O handler importa só o próprio serviço, `apperr` e `httpserver`; nunca o repositório nem
    `database/sql` (§2.2).
- `projects_integration_test.go`, com a pilha real de §10:
  1. `config.NewPaths` sobre uma pasta temporária com `programs\` e `EnsureLayout`.
  2. `db.Open`.
  3. `NewSQLiteRepository` e `NewService` com `installRoot = Paths.Root`.
  4. `httpserver.NewHandler` com token `"test-token"`, `cfg.Language` controlável pelo teste e
     logger num `bytes.Buffer`.

  O CT-60 também monta `preferences.NewService` + `NewFileRepository` sobre a pasta copiada.
